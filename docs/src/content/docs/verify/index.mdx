A receipt that only GLACIS can check is worth very little. The point of the
format is that the person who distrusts you can check it without our
cooperation, our uptime, or our permission.

## In a browser

**[glacis.io/verify](https://glacis.io/verify)** — paste a receipt, drop a JSON
file on the page, or open a verification link.

Everything runs client-side, using the browser's own WebCrypto Ed25519. The
receipt is not uploaded, not logged, and not sent anywhere. You can confirm that
by opening the network tab, or by loading the page, going offline, and verifying
anyway.

It reports each check on its own line rather than collapsing to a single
verdict:

| Check | What it establishes |
| --- | --- |
| Structural integrity | The required fields are present and well-formed |
| Signature (Ed25519) | The bytes have not changed since they were signed by the holder of that key |
| Hash binding | The parts of the receipt are bound together — you cannot swap one out |
| Merkle inclusion | The record was in the transparency log at the tree head shown — only when the receipt carries a transparency proof |

A missing check shows as *skipped*, never as passed.

<Aside type="caution" title="Which receipts the browser verifier reads">
  The verifier accepts GLACIS platform and gateway receipts — the format the
  hosted product and your workspace produce, which is also the shape described
  by [OVERT](/overt/).

  **Receipts produced by the Python SDK's offline mode are a different, flatter
  shape, and the browser verifier does not currently parse them.** Pasting an
  `oatt_…` receipt in returns *"Unrecognized receipt format"*. Verify those with
  the ten-line PyNaCl snippet in
  [Verify a receipt yourself](/verify/cli/#verify-a-receipt-yourself) — it does
  a real signature check, which is more than the CLI does.
</Aside>

## From a permalink

A verification link carries the receipt in the URL **fragment**:

```
https://glacis.io/verify#r=<base64url of the receipt JSON>
```

The fragment matters. Everything after the `#` is never transmitted in the HTTP
request — it stays in the browser. A receipt sent as a query string
(`?receipt=…`) would land in the access logs of every server and proxy between
you and the page; a fragment does not. Nothing about your receipt reaches a
server log by being shared this way.

Opening such a link verifies the receipt on load and shows the same per-check
breakdown.

<Aside type="note">
  The `#r=` fragment form ships with the launch build of
  [glacis.io/verify](https://glacis.io/verify). If the build you hit does not
  pick it up, paste the receipt into the box instead — same verification, same
  client-side execution.
</Aside>

## In Python

```bash
python -m glacis verify receipt.json
```

Read [what the CLI actually checks](/verify/cli/) before you rely on that
output. For offline receipts it is a structural check, not a cryptographic one.
The same page has a real verification routine that needs nothing but PyNaCl.

## Before you show anyone a green check

The three receipt states are not degrees of the same thing:

<ReceiptBadge kind="self-signed" gloss />

<ReceiptBadge kind="witnessed" gloss />

A valid signature on a self-signed receipt tells a third party that the bytes
have not been edited. It tells them nothing about when the record was made, and
nothing about whether the event described happened.
[What a check proves](/verify/what-a-check-proves/) sets out the boundary
precisely — it is the page to read before a receipt goes into a customer
questionnaire or a regulatory filing.
