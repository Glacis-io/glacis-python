Cryptographic verification is unusually honest for a security control: it either
holds or it does not, and there is no partial credit. What gets lost is that the
statement it makes is *narrow*. This page is the boundary, written down, so
nobody has to guess where it is.

## What a green check does establish

**The signed fields have not changed since they were signed.** A signature
covers a specific payload, not "the file". For an SDK offline receipt that
payload is built in `Glacis._attest_offline` and signed as
`json.dumps(payload, sort_keys=True, separators=(",", ":"))`. These are the
fields inside it:

| Inside the signature | Source |
| --- | --- |
| `version` | Constant `1` |
| `mode` | Constant `"offline"` |
| `service_id` | What you passed |
| `operation_type` | What you passed |
| `evidence_hash` | SHA-256 over canonical `{"input": …, "output": …}` |
| `timestamp_ms` | `str()` of the receipt's `timestamp` — so editing `timestamp` does break the check |
| `operation_id` | UUID grouping related attestations |
| `operation_sequence` | Position within that group |
| `control_plane_results` | Only when non-empty — the whole structure, not a hash of it |
| `supersedes` | Only when set |

**And these fields ride alongside the signature, not inside it.** Four of them
are inert — edit them and the check returns exactly what it returned before:

| Outside the signature, and inert | Consequence of editing it |
| --- | --- |
| `id` (`oatt_…`) | The signature still verifies. The identifier is not bound to the signed content. (It is not inert to the *routing* — see the next table.) |
| `cpr_hash` | The receipt still verifies. The control-plane *content* is signed; this convenience hash of it is not. The SDK additionally reports `cpr_hash_mismatch` by name when the two disagree, and still returns `valid=True` — the signature is the authority, not the hash. |
| `evidence`, `review`, `sampling_decision` | Not populated on offline receipts; adding them changes nothing about the check. |
| Any extra key you add to the JSON | Ignored entirely by the signature. |

Four more are unsigned and yet decide the outcome, which sounds like a
contradiction and is not: they are not *inputs to* the signed payload, they are
inputs to **the verifier**. Editing them does not forge a signature; it changes
which check gets run, or whether one runs at all.

| Outside the signature, and load-bearing | Consequence of editing it |
| --- | --- |
| `public_key` | Swapping it alone **breaks** the check. The key is not signed content — it *is the verifier*, so a receipt verified under a different key verifies nothing. What the key is not is bound to an identity: re-sign the same payload with your own key, swap both fields, and the result verifies perfectly. See *not that the signer is who they say they are*, below. |
| `cpr_recovery_error` | Never signed, never transmitted by the SDK, and set by *your* receipt store rather than by the signer: it means the store could not return the signed `control_plane_results`. When it is set the SDK **refuses** to verify and names it (`cpr_unrecoverable`), because the signed payload cannot be rebuilt. Editing it can therefore turn a good receipt into a refusal — never a bad receipt into a pass. |
| `is_offline` | Unsigned, and it **selects the verification route**. It does not select whether a signature is checked: `Glacis.verify()` runs the offline Ed25519 check on any receipt object you hand it, always. Setting it to `false` *adds* a lookup of the receipt's `id` on top, and that answer is applied to your receipt only if the two agree on `signature` and `evidence_hash`. Editing it can widen what is checked or narrow it — it cannot skip the signature. |
| `id`, when `is_offline` is `false` | Then the identifier chooses **which log entry gets fetched**, and a receipt that does not match the entry it points at is reported as unbound: nothing from that record is applied to it and `valid` is the receipt's own signature result. Pointing a receipt at somebody else's attestation therefore cannot borrow that attestation's verdict. |

All eighteen rows above are checked by tampering with a real receipt and
re-running the verification — ten signed fields that must break, four unsigned
ones that must not, and four unsigned ones that change what gets checked — and
the check script in `docs/scripts/` does it on every run. **"Altering any
character breaks the signature" is false**, and a verifier that implies
otherwise is overclaiming. What is true is that altering any *signed* field
breaks it, and that the four unsigned inputs to the verifier change the
outcome for reasons that have nothing to do with forgery.

<Aside type="caution" title="`is_offline` was described here as inert until 0.8.1.dev0">
  It was listed on this page as a field you could edit with no consequence, and
  in `glacis` 0.8.1.dev0 and earlier that was worse than wrong: `Glacis.verify()`
  picked its verifier *from* it. Setting `is_offline=false` and `id` to some
  valid online attestation routed the call to a server lookup, and the receipt
  you handed in — signature and all — was never examined. The server answered
  about the id; the caller read it as an answer about their bytes.

  Fixed in this repository, staged as 0.8.1 and unpublished: the offline
  signature check now runs on every supplied receipt object, and a lookup only
  speaks for a receipt that binds to the entry it returns.
</Aside>

<Aside type="caution" title="`control_plane_results` has to survive your storage, too">
  Being inside the signature cuts both ways: a receipt that **loses** its
  control-plane content stops verifying, because the payload can no longer be
  rebuilt. Up to and including `glacis` 0.8.0 the SDK's own receipt store did
  exactly that — it never persisted the field — so a receipt reloaded from disk
  failed independent verification although it had passed a moment earlier.
  Fixed in this repository and staged as 0.8.1, unpublished. If you are storing
  receipts yourself, store `control_plane_results` verbatim or you are storing
  something nobody can check.
</Aside>

**The signature was made by the holder of that private key.** The public key on
the receipt verifies the signature. Nobody without that private key could have
produced it.

**The input and output are committed to.** `evidence_hash` is SHA-256 over the
canonical JSON of `{"input": …, "output": …}`. If you hold the original input
and output, recompute the hash and compare — that binds the receipt to *that
specific exchange* and no other. Change a single character of the prompt and the
hashes diverge. (The exact canonicalisation, and where it diverges from RFC
8785, is on
[Quickstart](/connect/quickstart/#the-canonicalisation-actually-used).)

**Which controls ran, and what they returned.** When control-plane results are
attached, the structure itself is inside the signed payload. The record of what
scanned the text is as tamper-evident as the rest of the signed fields.

**For a witnessed artifact only: that the record existed at a time the author
did not choose.** The countersignature and the transparency-log inclusion proof
come from a party that is not the author. That is the property that makes the
timestamp mean anything to an outsider — and it is a property of the artifact
you are holding, not of a status string. See
[offline vs online](/connect/offline-vs-witnessed/).

## What a green check does not establish

**Not that the model output is correct.** A receipt over a hallucination is a
perfectly valid receipt. It records that the claim was generated, not that the
claim was any good.

**Not that the described operation ever ran in production.** Someone can attest
anything they can serialise. A receipt binds a *claim* to a signer; it does not
audit the system that made the claim. This is precisely why a receipt from a
form is a demo and a receipt from your inference path is evidence.

**Not that the input was honest.** The SDK hashes what your code hands it. If
your code hands it a sanitised version of what the model actually saw, the
receipt faithfully commits to the sanitised version. Receipts are only as
trustworthy as their position in the call path.

**Not compliance with anything.** No receipt makes a system compliant,
protected or certified, and this documentation will never say otherwise. A
receipt is evidence that a claim was generated. Whether that evidence satisfies
a particular obligation is a judgement for the person holding the obligation.

**Not that the signer is who they say they are.** A signature binds a record to
a *key*, not to an organisation. Tying that key to a legal entity is a separate
problem — key registration and workspace identity. Verifying a signature against
a public key you found in the same file you are verifying establishes internal
consistency, nothing more.

**Not, on its own, when it was signed.** A self-signed timestamp is a claim by
the signer about the signer. See below.

## The self-signed timestamp problem

<ReceiptBadge kind="self-signed" gloss />

The timestamp on a self-signed receipt is a field the signer chose. It is inside
the signature, so it cannot be changed *afterwards* — but nothing stopped it
being anything at all at the moment of signing, and nothing stops a whole batch
being produced this afternoon and dated last year.

<ReceiptBadge kind="witnessed" gloss />

A witnessed receipt is countersigned by a party that did not author it and
entered into an append-only log. The author cannot pick the time and cannot
quietly remove the entry later. That is the difference, and it is the only
difference that matters to a reader who does not already trust the author.

## Two tiers, two different claims

| | The claim | Safe to hand to |
| --- | --- | --- |
| <ReceiptBadge kind="self-signed" /> | "I say this happened, and I have not edited the signed fields since." | Yourself, your team, an internal reviewer. |
| <ReceiptBadge kind="witnessed" /> | "I say this happened; someone who is not me recorded that I said it, when I said it." | A customer, an auditor, an insurer, a regulator. |

## And one flag that cuts across both

| | The claim | Safe to hand to |
| --- | --- | --- |
| <ReceiptBadge kind="sample" /> | "This is what a receipt looks like. The signature over it is real; the operation it describes never ran." | Anyone, as an illustration. Never as evidence of an event. |

SAMPLE is not a third tier and it is not the opposite of "signed". A sample
receipt is <ReceiptBadge kind="self-signed" sample /> or
<ReceiptBadge kind="witnessed" sample />, and it passes exactly the checks its
tier earns. What it lacks is subject matter, not cryptography — which is why a
green check on a sample receipt is a demonstration of the verifier, and not a
statement about the world.

## How to read someone else's receipt

If a vendor hands you one:

1. **Check it yourself**, at [glacis.io/verify](https://glacis.io/verify) or with
   your own code. Do not accept a screenshot of a green check.
2. **Look at the badge.** Self-signed means you are being asked to trust their
   clock. Decide whether you do.
3. **Ask what the receipt covers.** `service_id` and `operation_type` say which
   system and which kind of operation. A receipt from a staging service is not
   about production.
4. **Ask for the coverage rate.** One receipt proves one event. A meaningful
   claim about a system is about the *proportion* of operations that produce
   receipts — a number that receipts alone cannot tell you.
5. **If it matters, verify the binding.** Ask for the input and output and
   recompute `evidence_hash` yourself. That is the step that turns "a signed
   record exists" into "a signed record about *this*".

<Aside type="caution" title="The failure mode to watch for">
  The dangerous reading of a receipt is not "this is forged". Forgery is what
  the cryptography actually prevents. The dangerous reading is a valid receipt
  about a narrower thing than the reader assumes: a real signature over a real
  record of a test call, presented as evidence about a production system. Read
  the fields, not the checkmark.
</Aside>
